The Account page — a canonical home for every admin tier

One page at /account, reached by clicking the whole bottom-left identity block in Shell.jsx. It gives Overseer, Super admin, and the new regular Admin a place to manage their own account — most urgently TOTP enrollment, which today hides on Team Management, a page the Admin tier can't even see. Built on the live rp-* system, clinical register, dark, no new tokens.

Design rationale

What populates the page, and why

Layout — single column, sectioned cards
Account management is low-frequency and personal. A second left-hand nav would fight the global nav already on screen; tabs would hide the one thing a new Admin came for (TOTP). A single readable column (max ~760px) with labelled section cards lets the eye fall straight to the hero and scroll the rest. It also matches the existing rp-body card rhythm.
Visual register
Clinical. Serif (Cormorant) headers, dark #080808, rp-* tokens, generous whitespace. No scripture forced onto a settings page — italic is reserved for scriptureItalic and there's no editorial copy that earns it here. Admins are competent: plain, honest labels, standard vocabulary (TOTP, 2FA), zero auth-internal jargon (no AAL2 / JWT / RLS on any surface).
Sections — baseline + what I'd add
baselineIdentity (name · tier · email) · Two-factor authentication · Sign out. (manifest § 3.5)
+ addActive sessions — sign out other devices. Real risk on a shared/observed machine; the shell already warns about unattended sessions.
+ addRecent account activity — this admin's own sign-ins (a "was this you?" mirror), not the global audit log.
+ addPreferences — timezone (logs render in it), language slot (localization lands later), notification cadence.
+ addDeactivation request — not self-service; routes to another admin.
excludedTheme switch (dark-only is locked), avatar upload (vanity + a security smell), data export (defer — little personal data here).
Team Management redundancy — my recommendation
Make the Account page the single source of truth for personal TOTP; pull the personal TOTP setup out of Team Management. Team Management is for managing others — burying your own second factor inside it is exactly what made enrollment invisible. Leave a one-line pointer on Team Management ("Manage your own two-factor authentication on your Account page →") for discoverability during transition. Clean separation: Team Management = team/tier ops; Account = self.

The hero · Two-factor authentication

TOTP — the reason this page exists

For a new Admin, this is the whole point. This component is already built — the CD does not touch it. Not enrolled renders the existing TotpEnrollmentScreen three-step flow verbatim, just hosted on this page instead of Team Management. Enrolled shows a calm status card — authenticator, enrolled date, last verified — plus a guarded Reset TOTP that runs the existing revoke + re-enroll.

Honesty of copy
Every action says what it does. "Reset TOTP" → "You'll set up your authenticator again from scratch." "Sign out other devices" → "Other devices will need to sign in again." No euphemism, no jargon — admins are competent and the stakes are real.
For Founder ratification

Open questions

Q1Team Management redundancy. Resolved → pull out. Personal TOTP setup moves off Team Management; the Account page is the single source of truth. A one-line pointer stays on Team Management for transition.
Q2Beyond-MVP scope. Resolved → all post-MVP. MVP ships identity + TOTP + sign out. Active sessions, Recent activity, and Preferences are approved as post-MVP follow-ups. Deactivation request is still under consideration (Founder dwelling).
Q3Recent activity scope. Resolved → aligned. This admin's own account events only (sign-ins, TOTP changes, sessions) — never anything leader-identifying.
Q4Cross-notify. Resolved → always-on. Ruth ↔ Replant Ops realtime is always-on system behavior; the page shows it as an Always on status line, not a toggle.
Q5Deactivation request routing. Leaning: the request surfaces in the Ops inbox. Open: does the requester keep access until it's actioned? (Founder still thinking — section marked under consideration.)
Q6Email editability. Email is read-only here. Is changing it ever self-service, or always an admin-mediated path? (Affects whether we add a "Request email change" affordance.)
