## Overall verdict

**NOT SUBMITTABLE. Five STORE BLOCKERS.** Three are hard guideline failures a reviewer hits inside two minutes of opening Settings or any UGC surface (account deletion, report, block); one is a submission-form impossibility (no privacy policy URL); one is aggregate placeholder density on the reviewer's natural path. The foundations underneath are genuinely strong (see "What held up") — the blockers are a bounded, enumerable set, not a rot.

## 2. Nutrition labels — PRELIMINARY draft (App Store Connect privacy details)

**PRELIMINARY — to be reconciled against the master data inventory from the parallel data-inventory lane before entry into ASC.** Basis: verified collection surfaces in code, Apple's definitions fetched live ("collect" = transmitted off-device and accessible beyond real-time servicing).

### Data Used to Track You
1. **None.** No ATT prompt needed. No ads, no data brokers, no cross-app identifiers. `NSPrivacyTracking=false` is true.

### Data Linked to You (all account-based collection; purpose = App Functionality throughout; no advertising, no third-party sharing beyond processors)
1. **Contact Info → Name** — first/last required at signup (structured name columns, KAN-229).
2. **Contact Info → Email Address** — required (auth identity).
3. **Contact Info → Phone Number** — optional (KAN-231).
4. **Location → Coarse Location** — church city/region attached to profile at registration; UG accounts excluded by DB CHECK (no city/lat/lng ever). Live GPS re-center is client-side camera movement; if any nearby-church query transmits coordinates they are serviced real-time and not retained — under Apple's definition that is NOT "collected." **Verify retention with the data-inventory lane before finalizing.**
5. **User Content → Emails or Text Messages** — DMs and branch messages (content + sender/recipients; flag pipeline processes content server-side).
6. **User Content → Other User Content** — prayer requests, testimonies, comments, heartcries (server-side encrypted), church profile content.
7. **Sensitive Info** — **required disclosure.** Apple's verbatim definition includes "religious or philosophical beliefs": role, church affiliation, and Declaration of Faith affirmation are religious-belief data linked to identity; arguably the entire account is. Do not omit this category.
8. **Identifiers → User ID** — Supabase auth/public user IDs.

### Data Not Linked to You
1. **Currently none from first-party code** — there is no analytics, crash-reporting, or usage SDK in the app (verified: no Sentry/Firebase/Amplitude/Segment in package.json or Podfile.lock).
2. **CONDITIONAL — Mapbox telemetry:** if Mapbox events remain enabled, declare per its manifest: Precise Location, Coarse Location, User ID (device-scoped), Product Interaction, Other Usage Data, Performance/Diagnostics — not linked, purposes App Functionality + Analytics. **Recommended path: disable telemetry and keep this section empty** (see verdict row 10).

### Notes
1. **Health data: not declared.** Pastoral/mental-health-adjacent disclosures live inside free-text User Content and are not collected as structured health data; declaring "Health" would over-claim. Reconcile with data-inventory lane.
2. Diagnostics: none collected off-device today. If crash reporting is ever added, labels must be revised first.

## 3. Submission checklist skeleton (App Store Connect)

1. **App record:** name (≤30 chars — decide casing; `CFBundleDisplayName` is currently lowercase "replant"), subtitle (≤30), keywords (≤100 chars), description, promotional text.
2. **Privacy policy URL** — blocked on LEGAL publishing the policy (STORE BLOCKER #4). Also wire the in-app Settings row to it.
3. **Support URL** — `website/` currently has no contact page; create one (doubles as 1.2(d) website leg).
4. **Screenshots:** 6.9" (iPhone 16 Pro Max class) required; 6.5"/6.7" set recommended. **iPad decision required:** `app.json` sets `supportsTablet: true` and the plist allows iPad landscape — that obligates 13" iPad screenshots AND an iPad-quality layout under review. Either QA iPad properly or set `supportsTablet: false` for MVP (Founder decision; propagate to Android tablet posture as the sister action).
5. **Age rating questionnaire (draft answers, new global system):** UGC = yes; user-to-user communication (chat) = yes; unrestricted web access = no; realistic violence = none-or-infrequent/mild (historical martyrdom descriptions in Witnesses); sexual content/profanity/horror/gambling/drugs = none; expected outcome ≈ **13+**. Confirm in the live questionnaire; do not guess it into metadata.
6. **Demo account:** pre-verified leader credentials on a seeded church + second account for two-way Connect flows (ask Founder which accounts; never assume Maranatha).
7. **Review notes draft:** explain the verification model (why fresh signups are gated), the covenant + flag-review moderation model, DELIVER-ALWAYS rationale, and contact info. **UG-feature disclosure depth = Founder/LEGAL ruling before drafting** (verdict row 18).
8. **Export compliance answers** per verdict row 13 — resolve the `ITSAppUsesNonExemptEncryption` decision BEFORE first submission (the plist key suppresses the ASC questionnaire, so a wrong key silently propagates).
9. **Nutrition labels** — enter after reconciling section 2 with the data-inventory lane; include Sensitive Info (religious beliefs).
10. **Build pipeline:** `eas.json` production profile exists (autoIncrement, remote versions); `submit.production` is empty — populate ascAppId/team when the ASC record exists. TestFlight: internal testing → external beta (note: external TestFlight goes through Beta App Review — the same blockers apply there, fix before external beta) → production submission.
11. **Localization:** English-only at MVP (Settings language row says "Coming soon"); `CFBundleDevelopmentRegion` en; `CFBundleAllowMixedLocalizations` not set and not needed while single-language. Declare English (U.S.) only in ASC — accurate, no action.
12. **Availability by country — callout (one paragraph, Founder/LEGAL):** default-all-countries is not obviously right for this app. App Store presence in hostile jurisdictions makes the app discoverable to hostile actors and its installation forensically legible on seized devices, yet excluding those countries denies the very leaders it serves (sideloading/store-region workarounds then become their only path, with their own risks). China's App Store additionally requires an ICP filing and has removed religious apps; Iran/North Korea have no App Store. Choose the availability list deliberately, with LEGAL, as a protection decision — not a distribution default.

## 4. What held up

1. **Privacy manifest posture is genuinely clean:** correct required-reason declarations for exactly the APIs in play; every SDK that needs a manifest has one; nothing on Apple's mandatory SDK list; no tracking.
2. **Zero surveillance surface from first-party code:** no analytics, no crash reporter, no ad SDK, no push. For this threat model that is a real asset — and it makes the nutrition labels short and true.
3. **4.8 is a clean N/A** — first-party email/password only.
4. **Signup data minimization is defensible as-built** (role/church directly relevant; church skippable; phone optional).
5. **Contact info in-app is real** — FAQ mailto plus accounts@ on five surfaces.
6. **Community-standards presence is better than most MVPs:** Declaration gate, covenant modal on first send (`covenant_ack`), covenant strips/footers on every composer and thread.
7. **Heartcry crypto is where the architecture says it is** (server-side pgp_sym; client is crypto-free on that path).
8. **Persecuted readers' fallback editorial is finished, dignified work** — KAN-254 is content ops, not a rejection vector.
9. **ATS strict** (`NSAllowsArbitraryLoads=false`), no background modes, portrait phone UI, `flag_taxonomy_secret.json` correctly untracked (gitignored, no git history) — AC-12 pattern secrecy intact.
