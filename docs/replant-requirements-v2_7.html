Screen 04 Account Setup — Page 2 (ASP2 — Church Search + Bypass Card)

Search (KAN-192)

Search input lives outside the ScrollView to defeat iOS's UITextInput.scrollRectToVisible override (KAN-192 keyboard-fix v3, Founder ruling 2026-06-12). Live debounced fetch fires after 3 characters. Accepts church name OR Replant Network ID (RPL-XXXXX). Cap-of-2 enforced server-side; rows past capacity render at 50% opacity with "Leader slots full" tag and block selection. Two empty states: (A) searched-no-results → "No churches found. / Try a different name or Replant ID, or register your church below." (B) pre-search → wireframe v4 card with magnifier + "Search by church name or Replant ID / to find your church."

Three church-attachment paths

  1. Join existing — tap a result row. Sets selectedChurch (truthy). Footer "Enter Replant" enabled. create-account v6 payload carries churchId.
  2. Register new — tap "Don't see your church? Register yours →" → navigates to RegCP1 → RegCP2 → returns to ASP2 with bypass card (see below). create-account v6 payload carries newChurch: {...}.
  3. Skip for now — tap "Skip for now" → modal "I acknowledge — Enter Replant." create-account v6 payload carries neither churchId nor newChurch. Leader gets users.verification_deadline = now() + 7 days (the skip-for-now countdown).

Paths 1, 2, 3 are mutually exclusive and each maps to a distinct welcome-email variant (see Email Trigger Map below) and a distinct auth-status-check response.

Bypass Card (orphan-prevention loopback — KAN-192 AC 5)

When RegCP2 validation succeeds, RegCP2 navigates back to ASP2 with the church payload persisted to OnboardingContext.loopbackChurch and a placeholder id 'local-draft' threaded through route params. ASP2's loopback useEffect sets selectedChurch + isNewChurchFromLoopback from those params, which triggers isLoopbackBypass. The standard search UI is replaced by a confirmation card:

  • ✓ Registered ribbon + inline "Edit" button (returns to RegCP1 with editChurch params)
  • Church name + meta row (type · city, country)
  • Named verification status row ("Awaiting verification" with description / "Verified" tag) — locked Founder copy via CD redesign 2026-06-13
  • Quiet "Made a mistake? Switch ›" link below the card. Tap → confirmation modal → on Confirm, clears OnboardingContext.loopbackChurch + route params (no BE call — no DB row was ever written under the v4 architecture). Card disappears, leader lands back on search.

The footer "Enter Replant" CTA is the SAME button across all three paths — it gates on canSubmit = !!selectedChurch && !capError (selected-church path) OR submits directly via the skip modal's "I acknowledge — Enter Replant" CTA.

Atomic-write boundary (orphan-prevention architecture, 2026-06-14)

No write operations hit the server until "Enter Replant" fires create-account v6. Read-only lookups (duplicate email check, church search, similar-church check) are permitted before submit. When the atomic RPC succeeds, the auth.users row, the public.users row, AND the church row (when newChurch was supplied) all materialise in a single PL/pgSQL transaction (public.create_account_atomic). Any failure inside the function rolls back all writes. The orphan-church window is structurally eliminated — verified on-device 2026-06-18 (test scenario #4: force-quit between RegCP2 and Enter Replant left zero rows in auth.users, public.users, public.churches).

Step-up Framework Architecture (KAN-46 Layer 4 + KAN-114 + KAN-117)

Sensitive admin actions require fresh password re-entry via the step-up modal before proceeding. Per SEC ratification ([KAN-114 comment 11256](https://projectreplant.atlassian.net/browse/KAN-114?focusedCommentId=11256)):

  • TIER 1 (require step-up, 14 actions): approve-church, reject-church, deactivate-church, reinstate-church, delete-announcement, post-announcement, grant-admin, revoke-admin, read-heartcry, mark-heartcry-responded, rag-override, seed-scripture, read-region, clear-flag
  • TIER 2 (no step-up, 1 action): escalate-flag (defensive direction; no exposure expansion)
  • TIER 3 (auto/meta paths, 2 actions): log-session-refresh, request-step-up

Token shape: HMAC-SHA256 JWT with { user_id, action, exp: now+TTL }. Action-binding contract: a token issued for action A cannot be replayed against action B (verified by validateStepUp({ expectedAction, expectedUserId, event }) at every consumer endpoint). Per-action TTL: default 5 min; read-heartcry tightened to 90s per SEC threat-model framing (life-safety surface). FE cache key: (userId, actionName) — cross-action replay structurally impossible at FE layer.
